# 10 FRAMEWORK PACKAGE (JOB F: `framework/`, the future Packagist library)
Binding. Load ONLY in a JOB F task (prompt asks to build/change `framework/`, namespace `Framework\`). Never for a module, adapter or delivery task.
GOAL: a Laravel developer finds the same shapes and habits (container, providers, config, routing, requests, resources, migrations, console, exceptions) running safely in WordPress. Once stable, `framework/` is published and projects consume it from `vendor/` unmodified.

## F1 BOUNDARIES
1 `Framework\` imports only PHP, WordPress (through thin adapters), PSR and `devlinkstudios/wp-service-container`. NEVER `App\`, `Core\`, a project name, table or config key beyond the documented ones.
2 Domain failures are recognized through PHP built-ins (`\DomainException` and subclasses), never a `Core\` class (breaks once `Core\` is rebranded).
3 Identity values (name, prefix, CLI prefix, REST namespace, views path) come from the project's `config/app.php`; library fallbacks are defaults, not identity.
4 `framework/` is never rewritten by the rebrander or forked per project; customization uses extension points (F4).
5 The framework knows no Domain concept (Result, Entity, Service).
6 Everything built for the framework ships as ONE package, including `devlinkstudios/wp-service-container` as a Composer `require` (never copied into `framework/`). Container changes happen in its own repo, then the version range is raised.

## F2 LARAVEL PARITY
Same name, signature shape and semantics as Laravel wherever WordPress allows; never reuse a Laravel name for different behaviour. Every deliberate difference is documented in the README ("Differences from Laravel": `$wpdb` transactions, `dbDelta()`, WP-Cron, four routing surfaces behind one `Route` facade). Present (per README): container wiring, config repository, helpers, dual routing (`routes/web.php`, `routes/api.php`), middleware pipeline, `FormRequest`/validator, `JsonResource`, exception handler, migration engine + Schema builder, console kernel + `make:*` + `php mini`, rebrander, lifecycle. Planned: Events & Listeners (`Framework\Events`) and Queues (`Framework\Queue`: Sync, WP-Cron, Action Scheduler, database drivers). Fluent Database is built but PAUSED for projects (11). Other candidates (logger, translator loader, cache, gates, mail, rate limiting): only when a prompt names them.
OPEN DECISION: Core adapters `WpEventDispatcher`/`WpQueueManager` forwarding to `Framework\Events`/`Queue` would require whitelisting those namespaces for Infrastructure (like 11 does for the database). Until decided, they use WordPress hooks/schedulers directly (08 E5, E7).

## F3 WORDPRESS-SAFE LIBRARY CODE
1 No side effects on include; no WordPress calls at file scope; hooks register in `boot()`. 2 No `ABSPATH` guard in library classes (entry files only). 3 WordPress is touched only through thin adapters (database, routing surfaces, filesystem, hooks). 4 Every global helper is wrapped in `if (! function_exists('name'))`. 5 Options, transients, hooks, table/CLI prefixes and cache keys derive from the project prefix passed in by a provider, never a hardcoded library string. 6 Escaping, nonce and capability primitives are provided (middleware, `e()`), so projects get the secure path by default. 7 Server faults never leak detail when `app.debug` is false. 8 Static state is per-plugin and resettable.

## F4 PUBLIC API AND STABILITY
Public API = what the README documents; everything else is `@internal`. Implementation classes are `final`; customization is via container bindings, providers, config, documented protected hooks (e.g. `Handler::mapDomainException()`), middleware, stubs. SemVer: removing/changing public behaviour = major; deprecate first (`@deprecated`, `E_USER_DEPRECATED` where safe); keep `CHANGELOG.md`. Consumers install into `vendor/`; Composer cannot technically stop edits there (protection = `composer install` restores it, `vendor/` is never committed): say so in the docs. Before the first tag, renames are not breaking; version 0.x until then.

## F5 PACKAGIST READINESS (report with command output)
[ ] `composer validate --strict` passes (name, type `library`, license, `php ^8.2`, `require` of the container and `psr/*`; confirm the final package name, README names `devlinkstudios/wp-mini-laravel-framework`). [ ] PSR-4 `Framework\` resolves every class after `dump-autoload`. [ ] `grep -rnE "\bApp\\\\|\bCore\\\\" framework/` returns nothing. [ ] No project identity literal outside documented defaults. [ ] Helpers guarded (F3.4), no include-time effects (F3.1), and no call to a global helper inside framework classes (D7): `grep -rnE "\b(config|app|view|base_path|env|route|redirect|to_route|old|e)\(" framework/ --include=*.php --exclude=helpers.php` shows none outside helper definitions. [ ] Rebrander works from `vendor/` (script path resolved from the project root) and leaves `Framework\` untouched. [ ] README: install, public API, differences from Laravel, upgrade notes; `CHANGELOG.md`; tag. [ ] This repo boots against the tagged package, not a path symlink. [ ] Prefix step proven (F6.5).

## F6 MULTI-PLUGIN COLLISION (DECIDED, D3)
WordPress loads all plugins into ONE PHP process; two plugins shipping `Framework\` fatal with "Cannot redeclare class". DECISION: at release build the whole dependency tree (`Framework\`, `DevLinkStudios\WPServiceContainer\`, `psr/*`, every require) is prefixed under the project's vendor prefix in the shipped zip (PHP-Scoper or a Mozart-family tool; Strauss is Mozart's maintained successor; choose at first release). Source keeps `Framework\`.
1 The prefix step runs at release build only, after the rebrander, and rewrites call sites in `app/` (and in `core/*/Infrastructure` if it ever imports `Framework\`). FROZEN folders never reference `Framework\`. 2 Prefixer-friendly code: no class names assembled from strings, no runtime reliance on the literal `Framework\`, no class-name strings in config. 3 Global functions/constants are NOT reliably prefixed, so framework internals never call a global helper (D7); helpers are project sugar. 4 Every bundled dependency is in the same prefixed tree. 5 Release evidence: the prefixed zip boots; no un-prefixed `Framework\` in shipped code; two prefixed sample plugins activate together. Action Scheduler is never bundled or prefixed (it version-negotiates itself): detect it with `function_exists`, list it as Composer `suggest`.

## F7 FORBIDDEN
Importing `App\`/`Core\`; naming a project/module/table; editing `vendor/`; vendoring a second framework copy; patching the framework from a module task; reusing a Laravel name with different meaning; features outside the prompt (YAGNI); hardcoded prefixes; unguarded global functions; include-time side effects; breaking documented public API without a major version; claiming Packagist readiness without F5 evidence.

## F8 DEFINITION OF DONE
[ ] Generic, no project knowledge. [ ] Laravel parity kept or difference documented. [ ] WordPress-safe (F3). [ ] Public API documented, internals `@internal`, SemVer impact stated. [ ] Touched F5 items re-verified. [ ] `app/` and `core/` not changed in the same step. (Tests paused.)
