# 09 AUTONOMOUS EXECUTION AND DECISION MAKING (STRICT; WordPress edition)
Binding. Load ALWAYS at the start of any step/module/plan execution (developer says "do step 3", "build the deal module", "continue the plan"). All AGENTS.md rules still apply; this file adds how to work without asking, verify, report and stop.

## A1 RANGE AND LAYOUT
You build the plan continuously across the requested range: execute each step in sequence, self-check, write its report, update logs, and move immediately to the next step in the range without stopping between steps. Decisions you take alone are recorded so the developer can improve AGENTS.md.
- **RANGE** = what the developer's request specifies:
  - Single step (`"do step 1.2"`): execute that 1 step, then stop.
  - Phase (`"execute Phase 2"`): execute all steps in that Phase sequentially without stopping between steps, then stop at Phase end.
  - Module (`"build the deal module"` or `"continue the plan"`): execute all remaining steps of the current unfinished module/phase sequentially in one continuous run (one session per module/phase, A13), stopping only at the end of that module/phase or on an A10 HALT.
```
docs/ai-plans/ (READ-ONLY): 00-MASTER-ROADMAP.md, <module>/ step briefs
docs/ai-reports/ (you write): PROJECT-LOG.md, DECISIONS.md, AI-HALT-LOG.md, NEXT-SESSION.md, <module>/<NN>-<step-slug>.md, <module>/00-module-summary.md
```

## A2 PRINCIPLES
1 STAY WITHIN REQUESTED RANGE; execute steps inside the range sequentially without asking permission between steps; touch nothing outside scope (A4 files excepted). 2 NON-BLOCKING: on a minor ambiguity or choice never halt to offer options; pick the safest standard path (A9), record it, continue. Halt only for A10. 3 VERIFY, DON'T ASSUME: every report claim needs evidence from files or command output; open a file before assuming a class/method/route exists. 4 REPORT HONESTLY: failed/partial/blocked are reported as such. 5 NEVER EDIT AGENTS.md, `.claude/rules/`, skills or the plan unless the brief says so; propose changes in the report. 6 LEAVE A TRAIL: a fresh session must continue from plan + reports alone.

## A3 PLAN AND STEP BRIEF
Roadmap = module order; a module with unfinished dependencies is not started (H1). Progress lives in `PROJECT-LOG.md` and reports, never the plan. NEXT STEP = first step in plan order not DONE/DONE_WITH_NOTES. Use the module folder name exactly. A brief has: STEP ID `<module>/<NN>`, MODULE, GOAL, INPUTS (schema/migration, files, earlier steps), SKILL/RULES, ACCEPTANCE, OUT OF SCOPE, SCOPE FILES (optional). A missing field: find it in the repo (migrations, earlier reports, existing modules); NEVER invent schema fields. A self-contradicting plan with no A9 resolution = H7; merely unclear = record an AMBIGUOUS BRIEF decision and continue.

## A4 IMPLIED IN-SCOPE FILES (never a scope halt; append-only)
`AppServiceProvider` (bind a Contract the step created, never change an existing binding); `app/Providers/<Module>ServiceProvider.php` + the `providers` list in `config/app.php` (inherent wiring when creating a module); `routes/web.php`/`routes/api.php` routes for the step's own controller actions via the `Route` facade inside the existing group; the module's own delivery files (controllers, FormRequests, `views/*.php`); additive Shared kernel additions (new Contract + adapter). Changing an EXISTING Shared contract/base class remains H6 unless the developer explicitly authorizes that exact existing artifact and the brief lists it in SCOPE FILES; this exception does not permit unrelated Shared changes. `docs/ai-reports/**`; files in SCOPE FILES. Anything else outside the module = H2. `framework/` and `vendor/` are never in scope (H12).

## A5 LOOP PER STEP (continuous inside requested RANGE)
S0 ORIENT: read AGENTS.md, the task's rule files and skill, roadmap, brief, PROJECT-LOG, DECISIONS, the previous report; respect earlier decisions unless wrong (record why); finish a non-DONE previous step first (A14). S1 PLAN: name the MODE of every path (AGENTS s2); list files to create/edit; LIST THE APPLICABLE RULE SECTIONS (PROCESS GUARD) before any code; CHECK FILE EXISTENCE for every file to create (`git ls-files <path>`); an occupied path the brief does not name = H10. S2 EXECUTE: in scope only, append-only on existing code, order CORE-PURE -> ADAPTER -> DELIVERY, decisions per A9 written down when taken; AFTER WRITING re-read the finished code against the S1 rule list. S3 SELF-CHECK (A6). S4 REPORT (A11): write concise step report and append to `PROJECT-LOG.md` / `DECISIONS.md`. S5 HAND OFF: if more steps remain in the requested RANGE, immediately advance to S0 of the next step without waiting for user input; stop ONLY at the end of the requested RANGE (A13) or if the current step ended `BLOCKED`/`FAILED`/`PARTIAL`.

## A5b RULE-TO-SKILL SYNC (after any rule, AGENTS.md or skill edit)
A step that edits AGENTS.md, `.claude/rules/**` or a `.claude/skills/**/SKILL.md` MUST sweep every skill for what the edit invalidated, before S3. Sweep with the old terms, not the new ones: the rename, class, path, rule-file name, route/helper or code shape you removed, plus the rule-file numbers you renumbered. The stale text still carries the OLD string, so searching for the new one returns nothing and reads as clean.
- Sweep scope: `.claude/skills/**/SKILL.md` always; `AGENTS.md` and `.claude/rules/**` when the edited artifact was a skill.
- Inside the step's write scope: fix in the same step, and report the file:line pairs as scope-authorized by this step's documentation scope.
- Outside it: do NOT edit. Report each hit under a `STALE_SKILLS_DETECTED` heading as a table — file path | line | quoted stale text | which rule it now contradicts | proposed fix. One row per hit; no prose summary in place of the rows.
- Zero hits: write `STALE_SKILLS_DETECTED: none — swept <term list> across <N> skill files`. An empty or absent heading is a failed sweep, not a clean one.
- Self-triggering: this section is itself a rule edit, so it is swept like any other.

## A6 SELF-CHECK (evidence per check: path:line or command output; no evidence = not PASS)
C1 files: planned files exist, no unexpected file. C2 scope audit vs S1 list/brief/A4; extras reverted or recorded as a deviation. C3 syntax: `php -l` per file (one per command), PSR-4 namespaces, `declare(strict_types=1);`. C4 `composer dump-autoload` after new namespace paths. C5 walk the Definition of Done of the applicable rule files (01 P6, 04, 05 R11, 06 T10) and the skill checklist against the code. C6 when `core/` changed: 06 T8 greps (A, B; C only after a port), report only real output. C7 wiring: each new Contract bound exactly once at the composition root; new routes exist (`routes/*.php`) inside the existing group using the framework's controller shapes. C8 schema fidelity: no invented/missed fields, exact types (`id` is `?int`). C9 no leftovers (`dd`, `dump`, `var_dump`, unfinished TODOs; list intentional ones). C10 runtime check only if the brief calls for it, via the developer's running local site (A8); remove data you created. C11 tests: report "tests: paused per policy", claim none. C12 transactions: every write in `TransactionManagerContract::run()` via `executeInTransaction()`; no transaction API in a Service; failure after a write is THROWN; row lock via `findByIdForUpdate()` inside the transaction; after-commit work after commit; manual flow forbidden; an unwrapped write is critical. C13 boundaries: delivery injects service contracts; no persistence exception in a Service; Entities `readonly class`, not `final`, never mutated by callers; module ports in the module provider listed in `config/app.php`; repositories use only `BaseWriteRepository`/`BaseReadRepository`/`$wpdb` (02 s7), no `Framework\Database\*` while Fluent is paused. C14 file existence verified beforehand. C15 rule-to-skill sync: when the step edited AGENTS.md, a rule file or a skill, A5b ran and its `STALE_SKILLS_DETECTED` table (or its `none` line) is in the report; not applicable otherwise. C16 repairs (when any A6b round ran): at most 2 rounds, no repeated Failure Signature, each repair bounded to the offending statement, contract changes scanned tree-wide for the bare name with `php -l` + signature compatibility, no A10 stop bypassed; each round's signature and outcome is in the report.
On failure: fix within scope and re-run (A6b); syntax errors, framework leaks, missing routes/bindings are fixed autonomously from AGENTS.md. Still failing after two repair rounds = PARTIAL/FAILED and stop (H8). Never DONE with a known failing check.

## A6b AUTONOMOUS FIX LOOP (bounded self-correction)
Philosophy: **diagnose first -> verify source -> make a bounded repair -> re-check -> detect flapping -> HALT safely.** The loop repairs *your own* in-scope work; it is not a licence to refactor, and it can never outrank a hard stop.
R0 ROUND ZERO is the initial A6 self-check. A repair round is one diagnose-repair-recheck cycle, not one edit; several edits in one round are fine while they serve one signature.
1 ROUNDS: at most **2 repair rounds** (Round 1, Round 2) after Round 0. Never a third. Round 2 failing = PARTIAL/FAILED, report, stop (H8).
2 FAILURE SIGNATURE: exactly `[error type + exact message] + [file path] + [line number]`. Nothing else — root cause, suspicion and intended fix are NOT part of the signature (they are what changes between attempts, so including them hides a repeat).
3 FLAPPING GUARD (H8): if the **same signature** returns after a repair, HALT at once with 0 further rounds. A repair that did not move the error means the diagnosis is wrong, not the edit; repeating it burns the budget and hides the real fault. A *different* signature starts a fresh round but still counts against the 2-round budget.
4 DIAGNOSE BEFORE EDITING: read the failing line and its method, name the rule it must satisfy and the signature, then edit. Never edit to "see if it helps"; an unexplained fix that appears to work is recorded as a RULE ERROR or an environment fault, not as a repair.
5 BOUNDED SCOPE: every repair touches only the method, statement or call that produced the signature. Rewriting a whole class, reformatting untouched methods, "tidying" adjacent code, or fixing a second failure found on the way is forbidden — each is a separate step. An architectural fix (purity leak, missing wrapper) is still bounded this way: move the one offending statement to its proper layer, do not restructure around it. Anything the fix needs outside the step's scope = H2, not a repair.
6 CONTRACT CHANGE SCAN: if a repair (or a step) modifies an Interface/Contract, scanning `implements`/`extends` is NOT enough — the name may be injected, aliased, type-hinted or referenced without either keyword. Scan the whole project-owned PHP tree (`app/ core/ framework/ routes/ config/ database/`) for the **bare contract name**, then for every hit run `php -l` and check **interface signature compatibility** (method names, parameter types, arity, return types, `?` nullability, defaults) against the new interface. A signature-compatible check is mandatory: a class can still load and fatal only when called. `framework/` and `vendor/` hits are REPORTED, never edited (H12).
7 A10 SUPREMACY: A10 H1-H13 can never be repaired, bypassed, relaxed or argued away by this loop. A hard stop fires immediately with **0 repair rounds**; the loop never runs before or around it. A repair that would require a forbidden action, a FROZEN-folder edit, a framework change, a secret, or a destructive act is a halt, not a round.
8 LOG: every round records signature, diagnosis, files/lines touched, result. Flapping or exhaustion is reported honestly with both signatures — never silently retried, never reported as success.
Never DONE with a known failing check; never a DONE that depends on an unrepaired round.

## A7 COMMANDS
ALLOWED without asking: read/list/search (`cat ls grep find`), `php -l <file>` (one file per command), `composer dump-autoload`, read-only `php mini` listings and read-only `wp` CLI, the 06 T8 greps, HTTP checks and read-only DB queries on the developer's already-running local WordPress site (never install, start or reconfigure one), any command the brief lists.
FORBIDDEN unless the brief lists it: migrations/seeders/anything changing schema or data; installing/removing/upgrading packages; running the test suite; git operations changing history or the remote (commit, push, reset, rebase, branch delete; never force-push or skip hooks); deleting files other than temp files you created; contacting external services or reading/writing secrets.
BASH SAFETY: no complex chaining (several `cd` and `&& php -l` in one string triggers prompts); clean single-file commands, paths instead of `cd`; COMPLETION SOUND once as its OWN separate command when the terminal work ends (01 P1.8); on any halt play the Interactive Alert (AGENTS s6).

## A8 ENVIRONMENT
No leftover background processes (reuse or stop; stop every server you started). Clean up rows/tokens/files/users you created (only what you can identify). On an interrupted call or dropped DB connection assess, clear the blocker, resume. Transient problems are retried up to 2 times, then stop safely, record the block, alert, halt without leaving the codebase half-written (H9).

## A9 DECISIONS
PRECEDENCE (highest first): 1 the developer's explicit instruction in the current brief, within scope (conflict with an AGENTS.md MUST: follow the brief, record a RULE CONFLICT); 2 AGENTS.md; 3 specific rule files (02-11) over 01; 4 skill snippets (reference only); 5 existing codebase conventions (verified by reading).
TIERS: 1 COVERED: a rule settles it, follow it. 2 GAP: decide per AGENTS.md as a framework-agnostic senior engineer: keep Domain/Application framework-free, depend on ports, smallest change, match the nearest module, reversible, nothing outside the step; record it. 3 CONFLICT: apply precedence, record a RULE CONFLICT. 4 HARD STOP: A10.
SCHEMA/RULE AMBIGUITY: mirror DB constraints (required, max length, FK existence, numeric defaults) as Entity invariants and FormRequest rules; do NOT invent business rules or semantic markers; defer complex logic and record the gap.
RECORD every Tier 2/3 decision at the time in the step report AND `docs/ai-reports/DECISIONS.md`:
`ID: D-<NNN> (never reused) | Step | Type: GAP/RULE CONFLICT/RULE ERROR/AMBIGUOUS BRIEF | Situation | Options considered | Decision | Basis (rule section or "no rule covers this: judgement: <reason>") | Impact (files, reversibility) | Proposed AGENTS.md change (exact wording or none) | Status: OPEN`.
RULE ERROR = a rule that is wrong, outdated or impossible to follow, or a rule file contradicting AGENTS.md: follow the safest reading and record it. Do not record routine choices, convention-following names or formatting. Never edit the rules to "fix" a decision.

## A10 HARD STOPS (HALT, alert, tell the developer exactly what is needed; NOTHING ELSE is a reason to stop)
H1 a required input cannot be found. H2 the step cannot be completed correctly without a change outside its scope (A4 files never count). H3 a destructive/irreversible action (deleting/overwriting work, changing data/DB, rewriting a possibly-run migration). H4 a security issue or a secret/credential/personal data would be read, written or exposed. H5 a forbidden A7 command is needed. H6 a decision breaks the architecture, needs a new technology the plan does not mention, or changes an EXISTING Shared artifact in a way that could break modules. H7 the brief contradicts itself and no A9 precedence resolves it. H8 a self-check still fails after two repair rounds. H9 an environment problem persists after two retries, the same step failed twice, or earlier steps may not be intact. H10 a file to CREATE already exists and the brief does not name it. H11 if your safety guardrails force you to halt and offer options (violating A2), log the reason in `docs/ai-reports/AI-HALT-LOG.md` once resolved. H12 FRAMEWORK CHANGE NEEDED: the step needs a feature in, or a change to, `framework/` or `vendor/`; JOB F is a separate task; never patch the framework or bypass it with a workaround. H13 FROZEN FOLDER EDIT: the step would edit a FROZEN folder (AGENTS s3) only to make porting or an adapter work; report which framework detail leaked and which port to add.
At a halt: set BLOCKED/FAILED/PARTIAL, write the report (done, needed), update PROJECT-LOG, stop. Independent later steps are NOT started.
HALT MESSAGE FORMAT (binding; three parts, in this order, before any other text — the developer resolves the blocker from this message alone, without opening a file):
1 BROKEN RULE / PREMISE: quote the exact section and sentence violated, path it (`AGENTS.md` §6 SCOPE; `09` A10 H10; `03` T4). A premise that fails rather than a rule — a file the brief assumes exists, a tool it mandates — is stated as such, with the check that failed.
2 CONFLICTING FILES: `path:line` for every artifact causing the conflict, with the offending text quoted. When nothing on disk conflicts because the conflict is between the brief and reality, say so and give the command output that proves it.
3 ARCHITECTURAL OPTIONS: 2-3 concrete options A/B/C, each with what it changes (files) and its trade-off, so the developer resolves it in one reply. Name the one you would pick and why (A9). A single-option message is a demand, not a halt.
Then: the Interactive Alert (§6), the BLOCKED report and PROJECT-LOG update (A11). Keep the three parts to the blocker; no background narrative.

## A11 REPORTS
Create folders/files if missing; EXISTING FILES WIN (keep their format and numbering). Reports are English; say "the developer", never a personal name. STATUS: DONE | DONE_WITH_NOTES | PARTIAL | BLOCKED | FAILED. Write the report even for BLOCKED/FAILED, and update PROJECT-LOG and DECISIONS before ending the step.
STEP REPORT `<module>/<NN>-<step-slug>.md`: `# Step <NN> - <title> (<module>)` / Status / Summary (2-5 sentences) / Inputs used / Rules and skills applied / Files (created, modified + one-line change, deleted) / Self-check table (Check | Result | Evidence, one row per C1-C14 and skill item) / Commands run / Decisions (D-IDs) / Deviations / Deferred and open items / Tests: "Paused per AGENTS.md" / Next step.
PROJECT-LOG line per step: `| <module>/<NN> | <title> | <status> | <decision count> | <report path> |`. AI-HALT-LOG entry: Date/Step, Dilemma, Why I Halted, Required AGENTS.md Fix.

## A12 MODULE COMPLETION
Write `<module>/00-module-summary.md`: final file tree (from the real filesystem), module-level check against the DoDs with evidence, decisions (D-IDs) by type, open items and intentional skeletons/TODOs, proposed AGENTS.md updates ready to copy.

## A13 FINAL MESSAGE AND HANDOFF
FINAL MESSAGE (short, factual): steps completed with statuses; BLOCKED/FAILED/PARTIAL and what is needed; number and most important new decisions; report paths; claim nothing unverified. MODULE-END: finish the summary and logs; overwrite `docs/ai-reports/NEXT-SESSION.md` (`Completed module | Next module (from the roadmap) | First step | Session name | Continue prompt: Continue the plan: <next-module> | Open decisions to review`; or "Plan complete"); start a new session for the next module ONLY if the environment provides a way, otherwise stop and repeat the values in the final message; never start the next module in this session unless the request named it.

## A14 RESUMING
Read `NEXT-SESSION.md`, roadmap, PROJECT-LOG, DECISIONS and the module's last report. Re-verify the last step's files on disk (C1, C3, C5 quickly); the filesystem is the truth. Finish a PARTIAL step first; a step with no report is unfinished: check the disk, complete it, then report. Disk and reports disagree: record a deviation, repair the report, continue only if nothing is lost (else H9).

## A15 ANTI-PATTERNS (each fails review)
DONE with a failing or unevidenced check; reporting from memory; stopping to offer choices A9 settles; quietly working around a rule problem; editing rules/skills/plan to make a decision official; out-of-step work; treating step-own provider/route registration as a scope violation; skipping or delaying the report; starting a step after a BLOCKED/FAILED one; a forbidden command; a write without a transaction boundary, a `DB::` facade or manual transaction call in a Service, after-commit work before commit; creating a file on an occupied path; a concrete Service in a Controller, a persistence exception in a Service; a mutated or `final` Entity; leftover servers/rows/tokens/files; long chained bash strings; inventing schema, rules, files, methods or routes; claiming tests while paused; starting the next module without being told; a rule/skill edit with no A5b sweep, or one reported as clean without the swept term list; a third repair round; retrying an identical Failure Signature; a repair that rewrites a whole class or method beyond the offending statement; a contract change verified only by `implements`; an A10 stop treated as repairable; a fix reported without its signature.

## A16 DEFINITION OF DONE FOR A STEP
[ ] Goal and acceptance met, in scope only. [ ] C1-C16 ran with evidence and pass. [ ] Any A6b round was bounded, non-flapping and logged with its signature. [ ] S1 rule sections re-read against the finished code. [ ] Applicable rule DoDs and skill checklist walked. [ ] Servers stopped, created data removed. [ ] Honest step report; PROJECT-LOG and DECISIONS updated; every decision has a proposed AGENTS.md change or "none". [ ] No rule file, AGENTS.md, skill or plan edited. [ ] Mode named; no edit in `framework/`/`vendor/`; D7 helpers only in `app/`, `routes/`, `config/`, views. (Tests paused.)
